# Deploy Clausewise on Zoho Catalyst Slate

This branch uses standard Next.js on Node and PostgreSQL. It does not require Cloudflare, Sites identity, or the Wrangler runtime. The prior Sites version remains in the `sites-runtime` branch. This is a single-owner review workspace; enterprise team access, OCR, vector retrieval and scheduled email remain outside this release.

## Prerequisites

- A Catalyst project and a new Slate application connected to this GitHub repository.
- A reachable PostgreSQL 14+ database. Zoho Catalyst Data Store is not PostgreSQL and cannot be substituted into `DATABASE_URL`. Database hosting is a separate dependency; check your provider's quota and charges. This repository does not create a paid database.
- A long owner password and generated session secret. Gemini is optional for uploads and manual review, required for AI questions.

## Console settings

1. Open your Catalyst console and create/select the project **Clausewise**.
2. Open **Slate**, choose deployment from GitHub, select `ganesh12456/Clausewise` and branch `main`. Use the existing-repository integration rather than importing a public repo into a second repository.
3. Set framework **Next.js**, runtime **Node.js 22**, root directory `/` (repository root), install command `npm ci`, build command `npm run build`. Use Slate's Next.js output handling (`.next` if a build/output directory is requested). Do not select Vite or use `dist`.
4. If a start command is requested, set `npm start`. The script selects `ZC_SLATE_PORT`, `X_ZOHO_CATALYST_LISTEN_PORT`, or `PORT` automatically and binds to `0.0.0.0`.
5. Run `npm run password:hash` in a private local terminal. Use a password of at least 16 characters. Save the password in your password manager; put only the generated hash and secret in Zoho's protected environment settings.
6. Set the environment variables below. Use the actual Slate HTTPS address for `APP_URL`. An initial deployment may be needed to obtain the address, followed by configuring `APP_URL` and redeploying. A missing setting produces a clear startup error instead of silently using temporary storage.
7. Deploy/redeploy. `npm start` applies the idempotent SQL schema under a PostgreSQL advisory lock before starting Next.js. If Slate manages the Next.js process directly instead of calling `npm start`, run `npm run db:migrate` against the same database once before opening the app. Migrations do not run during `npm run build`.
8. Open `/api/health`: expect HTTP 200 and `{"status":"ok"}`. Visit `/login`, sign in, upload a TXT contract, refresh, download its original, add an obligation and test its calendar export. Open **Settings → Connect Gemini**, enter the API key and model ID, save, then test the connection. Gemini credentials are configured through the app, not hosting variables. Confirm data survives redeployment before uploading real contracts.

| Variable | Value |
| --- | --- |
| `DATABASE_URL` | PostgreSQL connection string; use the provider's verified TLS connection settings |
| `APP_URL` | Exact HTTPS Slate origin, for example the address assigned by Zoho |
| `OWNER_EMAIL` | Email used to sign in; this does not send email |
| `OWNER_PASSWORD_HASH` | Output of `npm run password:hash` |
| `SESSION_SECRET` | Generated by the password script; keep private |

Set variables for the environment actually serving the app. Do not prefix secrets with `NEXT_PUBLIC_`. Do not commit `.env` or paste passwords/API keys into issues. Configure verified TLS using the database provider's instructions; do not disable certificate verification.

## Storage, login and migration notes

Original files are stored transactionally in PostgreSQL `bytea`, alongside contract records, review history and obligation links. This avoids ephemeral hosting disks and a separate object-storage credential for the initial release. Capacity is limited by the database provider. Each upload is capped at 20 MB, 100 pages and 1.5 million extracted characters. The browser supplies extracted text; server OCR and extraction validation remain future work. A document delete cascades to its original and linked obligations.

Login uses a scrypt password hash, an eight-hour signed HttpOnly session cookie, SameSite protection, origin checks, and a database-backed login-attempt limit. Rotating the password hash or session secret invalidates existing sessions. There is one configured owner; there is no public registration or email password reset. Change the owner email only as a deliberate data-ownership migration: existing records retain their original owner.

An existing Sites workspace's D1/R2 documents are not copied automatically. Export/download those documents before switching and re-upload them into Zoho if needed. Do not disable the existing site until the new deployment is verified. Configure database backups and restore procedures with your provider.

## Troubleshooting

- `cloudflare:workers` resolution errors: an old branch/commit is being deployed.
- Missing `DATABASE_URL`, invalid password hash, or missing `APP_URL`: configure the protected runtime settings, then redeploy.
- Database timeout: check provider firewall, network access, TLS and database availability.
- `relation records does not exist`: run `npm run db:migrate` with the deployment's connection string.
- Origin rejection at login: `APP_URL` must match the address in the browser exactly, including the scheme and any custom domain.
- Files work until restart: verify this code is deployed; it does not use the local disk for contract storage.

The connected Catalyst tools cannot create a new project or Slate app. The first project/app connection must be made in the console (or an authenticated Catalyst CLI). Existing deployment monitoring and redeployment can then use the connector.

## API keys from the frontend

After deploying and signing in, open Settings and use Connect Gemini. Save your API key and model ID, then Test connection. The test checks model metadata and sends no contract. You can replace or remove the key at any time. The existing database, APP_URL and owner authentication settings are still required before sign-in.

Migration `002_connections.sql` adds encrypted per-owner credential storage. `npm run db:migrate` now applies all committed idempotent SQL files. The API key is encrypted with AES-256-GCM using a key derived from SESSION_SECRET; it is never returned by the settings API or placed in browser local storage. Keep SESSION_SECRET stable: rotating it requires re-entering the saved API key. Old GEMINI_API_KEY/GEMINI_MODEL hosting variables are no longer used by this version.
